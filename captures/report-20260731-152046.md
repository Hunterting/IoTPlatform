## 八、已验证设计决策（empirical）

> 以下结论由 team-lead 用 python+paho 在 **同一台 EMQX broker** 上独立回环验证得出，
> 与 Phase 1 重构的某项设计决定相互印证，记录于此供 Phase 2 评审。

### 8.1 重叠订阅 EMQX 不去重

- 同时挂载 `#`、`/iot/server/#`、`/iot/server/iot-board/+` 三个重叠过滤器时，**同一条报文被投递了 3 次**。
- 说明该 EMQX 实例**不对重叠订阅做去重**：订阅多少次、同一消息就投递多少次。

### 8.2 「同 pattern 只订阅一次」是必需优化，不是可选

- Phase 1 重构决定：当 `WillTopicPattern == PublishTopicPattern` 时，**只订阅一次**（而非 will / publish 各订阅一次）。
- 本实证结论支持该决定：**若当初为 will 与 publish 各订阅一次（同一 pattern），线上每条设备报文都会被处理两遍**
  → 重复入库、规则引擎重复执行、告警重复触发。

**Q21 引用措辞**：

- 本结论**部分回答** Q21：已证实若两 pattern 相同则单订阅是必需。但遗嘱 topic 是否真的等于上行 topic，仍需通电断电抓遗嘱验证。
- 核对 `docs/ansheng-field-test-checklist.md`：**Q21 的主题是「遗嘱 `close` 报文的实际字段、顺序与触发条件」**（checklist 行 475），

### 9.2 从「工具验证通过」到「平台自动采集入库」还差什么

1. **建 ANSHENG_MQTT 协议配置记录**：在 `protocol_configs` 写入一条 `enabled` 的记录，
   含 broker 地址/端口/账号、上行订阅 topic、下行发布模板、QoS 等（值应与此工具所用一致：
   `120.79.3.248:18883`，上行 `/iot/server/#`，下行 `/iot/client/iot-board/{imei}`）。
2. **启动协议适配器**：ProtocolConfigService 加载该配置 → 启动 MQTT 客户端、按上行 topic 订阅、
   把收到的报文投递给 DataCollectionService。注意第八节的实证结论——同一 pattern 只订阅一次，
   否则每条报文被处理两遍。
3. **设备发现与认领**：设备首次上行后写入 `discovered_ansheng_devices`，再认领入 `devices` 表
   （绑定租户/点位/位置）。认领前平台不会把它当作「自己的」设备去采集。
4. **写入设备配置**：在 `ansheng_device_configs` 落设备级配置（如自动上报参数 `getDevStatusSec` 等）。
   **注意**：设备出厂为纯轮询模式，若不显式下发 `setAutoReport`，平台永远收不到主动上报（见 11.1）。
5. **数据落库链路**：DataCollectionService 解析 → 时序/明细表入库；接线告警与规则引擎。
   解析器必须按 method 分派 `tasks` 字段（见 10.2），并统一 `voltage/current` 的序列化（见 10.5）。
6. **落库 frameId**：延时/定时任务的 `sign` 就是下发时的 frameId，是设备侧任务主键（见 10.3），
   平台必须持久化 frameId 才能后续管理任务。
7. **端到端冒烟**：用本工具同款报文（或真实设备）发一条，确认能从 `devices` 认领一路走到入库，
   且采集到的 timestamp/状态与设备一致（呼应 Phase 1 的 timestamp 注入逻辑）。

### 9.3 为什么工具通过 ≠ 平台可用

- 本工具走的是 **直连 broker + 生产协议类（Builder/Parser/Catalog）** 的旁路，完全绕过
  ProtocolConfigService / DataCollectionService / 设备认领 / 入库 等平台链路。
- 因此它能证明「设备 ↔ 平台 的协议报文结构正确、Catalog 覆盖完整、时钟/timestamp 逻辑正确」，
  但**不能**证明「平台已配置好并能自动把报文变成库里的一条数据」。
- 当前 `protocol_configs = 0` 状态下，正式链路是「死的」：设备上线也不会被采集。

## 十、协议事实（实测结论 → 需向安圣确认 / 平台必须适配）

> 以下 5 条是从**真机原始报文**里读出来的结构性事实，不是推测。
> 每条都给出证据报文位置；对平台的影响写在「平台动作」里。

### 10.1 `slots` 是「每个插槽的状态数组」，不是「被操作的插槽号数组」——文档示例是错的

- **证据**：对 `slotNum:1` 下发 `action:"off"`，设备回 `"slots":[0]`。
  若 `slots` 是「被操作的插槽号」，回的应当是 `[1]`（插槽 1）；实际回 `[0]`，即插槽 1 的**状态为 0（断开）**。
  对照：`action:"on"` 回 `"slots":[1]`（状态 1=闭合）。同一插槽、两次动作、两个不同值 → 只能是状态。
- **推论**：`slots` 长度 == `slotAmount`（本机 =1），下标 = 插槽序号-1，值 = 通断状态。
- **文档冲突（硬问题，需安圣书面答复）**：文档示例写 `slots:[1,3,4]`。
  若 `slots` 是状态数组，`[1,3,4]` 意味着某插槽状态为 `3`、`4` —— **状态值不可能是 3 或 4**。
  该示例只可能是把「插槽号列表」误写成了 `slots`。**请安圣明确：`slots` 到底是状态数组还是插槽号数组？**
  （本轮已用 `actions` 下发 `slots:[1,3,4]` 做越界探测，结果见第四节 Q9 组。）
- **平台动作**：解析层按「状态数组」实现，并对 `slots.Length != slotAmount` 打告警日志。

### 10.2 `tasks` 同名异构：必须按 method 分派解析，禁止通用处理

- **证据**：
  - `getDevStatus` 响应里的 `tasks[]` 元素是**电参数快照**（含 `voltage`/`current` 等字符串数值）；
  - `getDelayTasks` 响应里的 `tasks[]` 元素是**延时任务对象**（含 `sign`/`enable`/`sAction`/`eAction`/`cnt` 等）。
- **两者字段集合完全不同，但键名都叫 `tasks`。**
- **平台动作（硬约束）**：`AnShengMessageParser` **必须按 `method` 分派** `tasks` 的反序列化目标类型。
  任何「看到 tasks 就按同一个 DTO 反序列化」的通用写法都会静默产生脏数据（字段全空或类型异常）。
  建议：`getDevStatus.tasks` → `SlotElectricSnapshot`，`getDelayTasks.tasks` → `DelayTaskEntry`，两个独立 DTO。

### 10.3 `sign` 就是下发时的 `frameId` —— frameId 被设备持久化为任务主键，平台必须落库

- **证据**：第一轮 `startDelayTask` 使用 frameId `000000d7621a7844`；
  随后 `getDelayTasks` 返回的任务对象里 `"sign":"000000d7621a7844"` —— **逐字符相同**。
- **含义**：frameId 不只是一次请求的相关性 ID，**它被设备当作该任务的主键长期保存**。
- **平台动作（重要）**：
  1. 下发 `startDelayTask` / 定时任务时生成的 frameId **必须落库**，与业务任务记录一一绑定；
  2. 否则平台重启后将**无法把设备上报的 `sign` 映射回自己的任务**，任务变成孤儿，无法查询/停止/审计；
  3. frameId 生成必须保证**全局唯一且不复用**（现实现 16 位随机十六进制，200 次抽样无碰撞）。

### 10.4 设备不校验下行 `timestamp` —— 协议层无重放保护

- **证据**：
  - 省略 `timestamp` 的下行命令（WiFi 形态报文）设备照常执行并应答 `ok`；
  - `setTime` 把时钟拨到 **+1h 的未来值**，设备照单全收并按该值应答，未做任何合理性校验。
- **结论**：`timestamp` 在下行方向**纯属信息性字段**，设备既不校验新鲜度也不做单调性检查。
- **安全影响**：任何能连上该 broker 并知道 IMEI 的一方，都可以**原样重放**一条抓到的控制报文，
  设备会再次执行。**协议层没有任何重放保护。**
- **平台动作**：
  1. 防护必须放在 **broker 侧**——按设备/租户做 ACL，严格限制谁能 publish 到 `/iot/client/iot-board/{imei}`；
  2. 生产环境**必须启用 TLS 与逐设备凭据**，禁止 `admin/public` 这类共享账号（当前联调环境正是共享账号）；
  3. 平台侧记录全部控制指令审计流水（谁、何时、下发了什么 frameId）。

### 10.5 同一物理量两种序列化：`EMdata[].v` 是 float32、`tasks[].voltage` 是 string

- **证据**（同一次 `getDevStatus` 响应内，同一路电压）：
  - `EMdata[0].v = 226.2900085` → **JSON number**，典型的 **float32 → double 提升噪声**（226.29 的单精度表示）；
  - `tasks[0].voltage = "226.290"` → **JSON string**，固定 3 位小数。
- **风险**：两条路径入库会产生**互不相等的同一物理量**（`226.2900085 != 226.290`），
  导致对账失败、去重失效、告警阈值在边界处抖动。
- **平台动作（二选一，必须统一）**：
  - 方案 A（推荐）：入库统一转 `decimal` 并 `round(3)`，与设备 string 侧精度对齐；
  - 方案 B：入库统一保留原始 string，计算时再转换。
  **禁止**两条路径各自入库各自的类型。
- **顺带**：`temperature` 实测为 **String**（回答 Q4），与 `EMdata[].v` 的 Number 不一致，同样纳入上述统一策略。
