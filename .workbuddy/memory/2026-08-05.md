## mqtt 存量隐患核查（代码级确认，本会话续查）✅ 根因坐实
- 用户选「核查 mqtt 存量隐患」→ 主理人独立核验链路, 确认这是**活动缺陷**（非仅历史数据问题）:
  - `MqttProtocolAdapter.cs:49` `JsonSerializer.Deserialize<MqttProtocolOptions>(connectionString)` **无 options → 大小写敏感**;
  - `MqttProtocolAdapter.cs:332-335` `MqttProtocolOptions.Host`(默认"localhost")/`Port`(默认1883) 为 **PascalCase**;
  - `ProtocolManagementPage.tsx:953-954 / 963-964` **通用 mqtt 表单仍写小写 `host`/`port`**（AnSheng 分支已修 PascalCase, 但通用分支在 T12-BugFix 时只加了互斥隐藏、未改大小写）; 详情区 726-735 也读小写。
  - 数据流 `ProtocolConfigService` 对 Config 无 key 归一 → 小写 key 直达适配器, Host/Port 静默落 localhost:1883。
- **结论**: 凡经该 UI 建/改的 MQTT 协议配置（Broker 非 localhost:1883）实则一直静默连错 Broker；即便 DB 原存 PascalCase, 经 UI 编辑保存也会被改写为小写而损坏。属生产级静默故障。
- **修复方案评估（待用户确认是否开工）**:
  - 首选 **后端一次性修复**: 给 `MqttProtocolAdapter`(及 `AnShengMqttProtocolAdapter`) 的 `Deserialize` 注入共享 `JsonSerializerOptions { PropertyNameCaseInsensitive = true }`。好处: 一招修 mqtt + 存量小写数据无需迁移 + 安圣 PascalCase 仍兼容; 风险极低（扁平 DTO 无键冲突）。
  - 次选 前端改 PascalCase（Host/Port/Endpoint/...）: 仅修新建, 存量 DB 行仍小写直到被重存, 且需逐适配器对齐大小写, 脆弱。
  - 建议: 后端 case-insensitive 为主, 前端通用表单小写键可保留（向后兼容）或后续对齐, 非阻塞。
