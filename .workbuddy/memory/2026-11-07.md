## 租户登录日志不可见 — BugFix（+ 回归 + 真机复验）

### 现象
用户报：租户登录后「登录日志管理」看不到登录日志。

### 根因（双链路定位）
- 前端 `LogManagementPage` 是纯透传：请求不带租户标识、回包不做 appCode 过滤、菜单靠 `hasPermission('view_logs')` 控制（已不读静态 DEFAULT_ROLES，以服务端 `UserDto.permissions` 为准）。前端无 bug。
- 后端根因在**写入**：`AuthService.RecordLoginLogAsync` 没把已算好的 `effectiveAppCode` 传给 `LogRepository.LogLoginAsync`，后者构造 `LoginLog` 也不赋值 `AppCode` → 每条登录日志 `AppCode` 恒为 NULL；而 `GetLoginLogsQuery` 用 JWT 的 AppCode 做 `WHERE AppCode == 租户` → 租户查询永远 0 条。超管不签 AppCode claim + 过滤器短路 → 看全量（含 NULL 行），故「超管可见、租户不可见」。
- 次级缺口：staff/chef/operator/customer_admin/user 静态权限集（及为 null 的种子 Permissions）不含 `VIEW_LOGS`，被 `LogsController` 控制器级 `[PermissionAuthorize(VIEW_LOGS)]` 整组 403，连页面都进不去。

### 修复（P0 + P1）
- P0（寇豆码）：`ILogRepository.LogLoginAsync` / `LogRepository.LogLoginAsync` 加 `appCode` 参数并赋值 `LoginLog.AppCode`；`AuthService.RecordLoginLogAsync(user, success, appCode)` 透传，`LoginAsync:147` 调用处传 `effectiveAppCode`。新增迁移 `20261107023459_BackfillLoginLogAppCode`：`UPDATE login_logs SET AppCode=(SELECT u.AppCode FROM users u WHERE u.Id=login_logs.UserId) WHERE AppCode IS NULL;`（用真实表名）。
- P1（用户拍板「全部租户角色」）：`Configuration/RoleConfig.cs` 的 admin/operator/chef/staff/customer_admin/user 静态权限集均加入 `Permissions.VIEW_LOGS`；新增 `CUSTOMER_ADMIN`/`USER` 常量与 `GetCustomerAdminPermissions()`/`GetUserPermissions()`。

### 测试与验证
- 严过关：30 新用例全绿（20 单元 + 10 集成真实 MySQL）。覆盖 RoleConfig 全租户角色含 VIEW_LOGS、AppCode 落库(InMemory)、租户隔离、6 角色 `GET /logs/login`→200（修复前 403）、无 view_logs 自定义角色仍 403、超管看全量。

- 真机：`direct-DLL + Staging` 重启（task jC6OeZ，:5000，hosting=Staging，自动迁移 no-op），MQTT 连真机/设备实时上报正常；超管登录→`GET /logs/login` code 200、返回带 appCode 字段的记录，超管自身日志 appCode=null（符合预期）。

## 权限清单数量漂移 — 根治

### 背景
QA 早前发现 `Permissions.All`(75) 与 `GetSuperAdminPermissions()`(70) 数量不一致（技术债）。根因：后两者是手写副本，新增常量未同步。

### 修复（寇豆码 / software-engineer-4，最小侵入、未 commit）
- `Roles.GetSuperAdminPermissions()` 整体改为 `return Permissions.All;`（保留 `<summary>` 说明历史漏授）。

- `GetPermissionDescriptions()` 补 8 条缺失描述（区域增改删 / 网关·隧道配置 / 设备指令 3 项）。
- `GetAdminPermissions()` 不变：仍先 `GetSuperAdminPermissions()` 再 `Remove` API 配置 → `admin ⊆ super_admin` 契约维持（现在 admin = All 去掉 API 配置）。

## 租户管理员设备列表看不到数据 — BugFix（区域白名单脏数据）

### 现象
用户连续两次报：登录**租户管理员**（manager@haidilao.com / admin123）在「设备列表」看不到任何数据。

### 根因（推翻了所有同源家族猜测，真机逐层证伪）
不是 AppCode、不是权限、不是前端、不是全局查询过滤器，而是 **区域白名单 `AllowedAreaIds` 指向不存在的区域 ID**：
- `GET /api/v1/devices` 读路径：`DevicesController.GetAllowedAreaIds()`(:220-229) 从 JWT claim `AllowedAreaIds` 读出 → `Repository.ApplyFilters`(:192-224) 叠加 `WHERE AreaId IN (...)`（要求 `AreaId.HasValue && allowedAreaIds.Contains(AreaId.Value)`）。
- `SeedUsers.cs` 把租户用户 `AllowedAreaIds` 写死成假 ID：manager=`"1,2,3"`、operator=`"1"`、user1=`"1,2"`、chef=`"1,2"`、staff=`"1"`；超管=null。
- `areas` 表 customer_001 真实区域 ID 是 **11/12/13/14/15**（层级 11→12→13→15），**没有 1/2/3**。
- `devices` 表唯一设备 Id=7（安圣4G开关，2026-11-05 认领）`AppCode=customer_001`、`AreaId=15`（厨房区）。
- 于是 `15 NOT IN (1,2,3)` → 设备被区域过滤清空 → code=200 / items=0。

### 关键证伪链（主理人真机 :5000 实测，勿再走弯路）
- 侦察工程师初判「存量 devices AppCode=NULL」被 DB 实测推翻：devices 仅 1 行、AppCode=customer_001、异常行 0。
- 又猜「staff 缺 VIEW_DEVICES → 403」也被推翻：operator(staff) 调 /devices 返回 **code=200 / items=0**（运行时 DB 驱动角色权限给了 VIEW_DEVICES，静态 RoleConfig 表不是运行时事实来源）。
- **决定性反证**：超管 JWT 无 `AllowedAreaIds` claim → 不加区域过滤 → 看到同一台设备(7)；admin JWT 有 `AllowedAreaIds=1,2,3` → 0 条。两者唯一差异就是该 claim，锁定真因。
- JWT 的 `AllowedAreaIds`/`AppCode` claim 是**登录时**从 DB 签发进 token 的 → 改 DB 后必须**重新登录**才生效（旧 token 不变）。

### 修复（用户拍板「把租户管理员账号的 AllowedAreaIds 追加区域15」，范围严格收敛）

## 生成数据库创建脚本（EF 迁移幂等全量）

### 用户拍板
「EF 迁移幂等全量脚本（推荐）」——Code-First 项目，schema 权威来源是迁移，不手写 DDL。

### 侦察事实
- `Migrations/` 16 个真实迁移（+ ModelSnapshot），真实库 `__EFMigrationsHistory` 已应用 16 个，链完整无缺口；`AppDbContext` 46 个 DbSet。
- `dotnet-ef 8.0.0` 可用；`Data/AppDbContextFactory.cs`（IDesignTimeDbContextFactory）存在，EF 走 factory + StopTheHost 截断 host build，**不触发** `Program.cs:422 Migrate()` 也不触发 Development DataSeeder 清库。
- 种子独立：`Data/SeedData/` 6 个 Seeder，迁移脚本本身不含种子 INSERT。

### 产出
- 命令：`dotnet ef migrations script --idempotent --no-build --project IoTPlatform.csproj --startup-project IoTPlatform.csproj -o scripts/create-database-idempotent.sql`（`--no-build` 直接复用 `bin/Debug/net8.0/IoTPlatform.dll`，避开被 :5000 锁定的 DLL；未执行 dotnet build / dotnet run）。
- 产物：`scripts/create-database-idempotent.sql`，4406 行 / 139539 字节。
- 主理人独立核验：CREATE TABLE=47（46 业务表 + __EFMigrationsHistory）、IF NOT EXISTS=253（252 守卫 + 1 bootstrap）、历史表 INSERT=16（每迁移 1 条）、16 个 MigrationId 全命中、CREATE DATABASE=0 / DELETE FROM=0 / 种子 INSERT=0。

### 方言要点（重要）
Pomelo/MySQL 幂等脚本用**存储过程 `MigrationsScript` + `DELIMITER //`** 包裹每个迁移的 `IF NOT EXISTS(SELECT 1 FROM __EFMigrationsHistory WHERE MigrationId=...)`（MySQL 不允许顶层 IF，非 SQL Server 的 `BEGIN...END`）。**必须用支持 DELIMITER 的客户端执行**（mysql CLI / Navicat / DataGrip），不要用逐句拆分的通用 SQL 执行器。脚本含 1 条迁移自带合法 DML：`BackfillLoginLogAppCode` 的 `UPDATE login_logs SET AppCode=...WHERE AppCode IS NULL`，被幂等守卫包裹，属迁移链内容非种子。

### 现场保护（工程师 + 主理人双验）
后端 :5000 Staging 未停/未重启、DLL 未被覆盖、真实库未改动（__EFMigrationsHistory=16、users=6、roles=7、customers=3、devices=1、login_logs=207）、未 commit。工作区新增 `?? scripts/create-database-idempotent.sql`（+ 之前未提交的 memory、SeedUsers.cs）。

### 使用注意
- 脚本不含 `CREATE DATABASE`，执行前须先 `CREATE DATABASE iot_platform CHARACTER SET utf8mb4;` 并 `USE`。
- 幂等：可在已有库重复跑，已应用迁移自动跳过。
