## 安圣协议冷启动自动拉起 —— 立项（未实现）
- 来源：2026-10-27 联调发现待认领池空，根因为后端重启后活跃协议未自动拉起（详见 `2026-10-27.md`「续3」）。用户 2026-10-28 指令：「先按这个方案立项，后续如有需要再实现」。
- 状态：**已立项，未实现**（代码留待需要时落地）。
- 标题：协议配置冷启动自动拉起（`ProtocolConfigAutoStartHostedService`）
- 背景：每次后端重启/部署后，活跃协议不会自动 `StartProtocolAsync`，运维须手动 `/start`，否则设备上行静默丢弃（无报错、待认领池恒空）。T12 真机联调能跑通正是因当时手动 `/start` 过。
- 方案概要：
  - 新增 `IHostedService`（BackgroundService 或 `IHostedService` 实现），在 `ApplicationStarted` 生命周期钩子里执行。
  - 拉起范围：遍历 `ProtocolConfigs` 中 `IsActive == true && ProtocolType 非空` 的配置，逐个调用 `IProtocolConfigService.StartProtocolAsync(id, appCode)`。
  - **复用现有双条件短路判活**（`ProtocolConfigService.cs:464-486`）：DB=active 但内存无适配器才走完整启动，避免重复订阅炸弹；与现有 `/start` 路径完全一致，不另写启动逻辑。
  - 启动失败（如 broker 不可达）应 catch 记 WRN 不阻断宿主启动；拉起动作在 hosted service `StartAsync` 内 await 即可，与 `app.Run()` 解耦。
- 边界 / 非目标：
  - 不改动发现/采集/桥接逻辑；不新增配置管理 UI。
  - 不改 `StartProtocolAsync` 现有契约（含 `ReconcileDerivedFields` 幂等补齐、派生字段同步）。
  - 仅拉起持久化为 active 的配置；inactive 不动。
- 验收标准：
  1. 后端 cold start（direct-DLL + Staging）后，无需手动 `/start`，日志出现 `已订阅安圣数据主题` + `协议已启动`。
  2. 真机上行在重启后无需人工干预即自动进 `discovered_ansheng_devices` 待认领池。
  3. 重复重启不产生重复订阅（static 订阅表 + 双条件短路生效，无 N 倍报文）。
  4. 新增/补充单测 + 集成测试（可复用 `ProtocolLifecycleHardeningTests` 骨架与 `FakeProtocolAdapterFactory` 重启开关）。
- 优先级建议：P1（运维可靠性，当前为人工隐患）。
- 关联铁律：DI 生命周期错配铁律（`ProtocolConfigService`=Scoped，hosted service 调用须新开 Scope 解析，参考 `Program.cs:484` 强制解析模式）；新进程级静态态须纳入 `StaticStateResetter.ResetAll`。
