## BugFix：认领选区域后设备列表不显示区域名（实际是租户 GET /devices 全 500）

### 现象
- 用户反馈：「设备认领选择了区域，保存到设备在设备列表页面没有显示区域，区域 id 有保存到」。
- DB 复核：设备 Id=7（AppCode `customer_001`）`AreaId=15`=「厨房区」，同 AppCode；super-admin API 直出 `"areaName":"厨房区"`。
- 前端链路 `DevicesPage.tsx:321` → `device.area` ← `deviceAdapter.adaptDeviceDtoToDeviceItem`（`area: areaName || '未分配区域'`）← `DeviceContext.loadDevices` 映射 → 全部正确，可排除前端映射 / DTO 填充 / 多租户过滤排除。

### 根因（`Data/Repositories/Implementations/Repository.cs` `ApplyFilters` 区域权限过滤分支）
- 旧代码：`Expression.Call(typeof(List<long>).GetMethod("Contains", new[] { typeof(long) }), constant, value)`，其中 `constant` 是 `allowedAreaIds` 列表、`value` 是 `AreaId.Value`。
- 反射把 `List<long>.Contains` 解析为**静态方法**，而调用时又把列表作为**实例参数**传入 → 触发 `System.ArgumentException: Static method requires null instance, non-static method requires non-null instance.`
- 该分支仅在租户携带 `AllowedAreaIds` JWT 声明时进入；**super-admin 无此声明 → 分支跳过 → super-admin GET 一切正常**，这正解释了「为什么只有普通租户崩、超管正常」。
- 异常被 `DevicesController.GetDevices` catch 后由 `ApiResponse.Error(ex.Message)` 直出 HTTP 500（未进 `ExceptionHandlingMiddleware`，故 Serilog 文件槽也无痕），导致**整个设备列表加载失败 / 不刷新**，表现为「认领时区域 id 存了，但列表里看不见区域」。

### 修复
- 改用静态泛型写法构造表达式树，消除实例/静态歧义，且 EF Core 可正确翻译为 SQL `IN` 子句：
  ```csharp
  var containsMethod = typeof(Enumerable)
      .GetMethods()
      .First(m => m.Name == "Contains" && m.GetParameters().Length == 2)
      .MakeGenericMethod(typeof(long));
  var contains = Expression.Call(containsMethod, constant, value);
  ```
- 仅此一处功能性改动，未动其它逻辑。

### 验证
- `dotnet build` 0 错 → direct-DLL + Staging 重启（task `fZIaae`）。
- 临时给 `manager@haidilao.com` 授权 AllowedAreaIds 含 15 → 租户 `GET /api/v1/devices` 返回 `{"code":200,"data":{"items":[{"id":7,"areaId":15,"areaName":"厨房区",...}]}}` ✅（授权为纯测试，已回退 DB）。
- 诊断脚本 `diag_*.py` / `diag_ex.txt` / `backend_console.log` 均删除；`git status --short` 确认 `Repository.cs` 在修改未提交之列。

### 结论
- 区域不显示的根因不是字段没存，而是**租户设备列表接口 500 使前端拿不到数据**。修复后 `areaName` 正常出网、前端正确展示。
- 全部改动（Intent O 认领字段 + P1 自动拉起 + 本修复）仍 **未 commit**，留工作区待决策。

## BugFix：AlertService 手动事务与 MySQL 重试策略冲突（18:35 用户「修复这个bug」）

## 全局 DateTime 出网格式统一（19:14 用户「日期字段只需要秒、时间要准确」）

### 用户 AskUserQuestion 拍板
- 范围 = **全局统一**；格式明确 **`2026-11-05 19:17:00`**（空格、到秒、无 T/Z/微秒、本地墙上时间）；时区口径 = **「不需要」**（不要 UTC+Z 那套，也不要前端再换算，后端直接给直观准确的本地时间）。

### 根因（实测坐实）
- 服务器时区 = 中国标准时间 UTC+8（python `time.tzname`）；全项目 **268 处写 `DateTime.UtcNow`**（库里存 UTC），仅 1 处 `DateTime.Now`。
- MySQL 读回 `DateTime.Kind=Unspecified` → `System.Text.Json` 默认出网 `2026-11-05T11:17:00.123456`（UTC 值、带 6 位微秒、**无 Z 后缀**）。
- 前端 `new Date(str)` 把无时区后缀串按**本地**解析 → 中国用户看到比真实少 8 小时（UTC 11:17 被显示成 11:17，实际本地 19:17），且拖一长串微秒。
- `Program.cs:311 AddJsonOptions` 原本只注册 `JsonStringEnumConverter`，**无任何 DateTime 转换器**；`datetime(6)` 列分布在 27 个迁移文件（全库既有约定，不刷库）。

### 实现（主理人直接实现，4 文件）
1. `Helpers/LocalDateTimeJsonConverter.cs`（新）：`JsonConverter<DateTime>`。
   - **Write**：`Unspecified`/`Utc` → `SpecifyKind(Utc).ToLocalTime()` → `ToString("yyyy-MM-dd HH:mm:ss")`；`Local` 直用；`DateTime.MinValue` 特判输出 `0001-01-01 00:00:00`（避免 +8 变 `08:00:00`）。
   - **Read**：宽容解析——带 Z/±HH:mm 用 `DateTimeOffset.TryParse` 转 UTC；无标记的按**本地时间**解析再 `ToUniversalTime()`（与 Write 对称）；精确格式数组 + `DateTime.TryParse` 兜底。
   - System.Text.Json 会用 `NullableConverter<DateTime>` 自动包装，**`DateTime?` 同样生效**（实测 `authorizedAt/expireAt` OK）。
2. `Program.cs`：`AddJsonOptions` 追加注册该转换器（加在 `JsonStringEnumConverter` 之后）。**不动 268 处 UtcNow、不刷库、DB 仍存 UTC**（兼容历史数据 + 944 测试）。
3. `Services/DeviceAuthorizationService.cs`：加 `TruncateToSecond`/`UtcNowSecond`，把 `now`/`expireAt`/`AuthorizedAt`/`CreatedAt`/`UpdatedAt`/`AlertTime`/禁用判定统一截断到秒（新数据「保存只需要秒」、天数计算边界稳定）。
4. `tests/.../IntegrationTestBase.cs`：`JsonOptions` 追加同一个 `LocalDateTimeJsonConverter`（其注释本就写着「与服务端 AddJsonOptions 保持对称」）。
