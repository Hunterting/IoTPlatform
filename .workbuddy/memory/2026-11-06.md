## 用户管理两模块（用户列表 / 角色管理）租户隔离核实（15:08 用户问询）

### 结论
- **两个模块都按租户（AppCode）隔离**，机制是「全局 EF 查询过滤器 + 仓储层 AppCode 过滤」双层叠加。
- `User`/`Role` 均实现 `IHasAppCode`（`Models/User.cs:8`、`Models/Role.cs:8`），故 `AppDbContext.ConfigureGlobalQueryFilters`(:169-203) 在 DbContext 构造时对它们挂 `WHERE AppCode = _tenantContextAccessor.Current.AppCode`（超管 / AppCode 为空 → 不过滤）。
- 各 Service 又把 JWT 的 `AppCode` 透传给仓储 `GetQueryable(appCode)` → `Repository.ApplyFilters`（:168-189）在 appCode 非空时再拼一层 `WHERE AppCode = appCode`。
- 行为：超管看全部；带 AppCode 的租户只看本租户行；**两种情况都对**（双层同值 AND）。

### ⚠️ 坑 1（角色创建不落 AppCode，真 bug 级）
- `RoleService.CreateRoleAsync`（:103-128）显式 `AppCode = null`（注释「新角色默认为系统级」）。后果：租户自建的角色 `AppCode=NULL`，而租户列角色走 `AppCode = 'tenantA'` → SQL `NULL != 'tenantA'` → **创建者自己都看不到该角色**（仅超管无过滤可见）。即「租户建的角色变全局角色 + 自己还列不出来」。用户列表则正确：`UserService.CreateUserAsync`（:169）落 `AppCode = customer?.AppCode`。→ 角色模块需补「按当前租户 AppCode 落库」逻辑（与用户模块对齐）。

### ⚠️ 坑 2（全局过滤器静态表达式固有缺陷，已知）
- `ConfigureGlobalQueryFilters` 在 DbContext 构造时一次性用 `_tenantContextAccessor.Current.AppCode` 捕获表达式（:172-200）。若同一 DbContext 生命周期内 AppCode 变化，过滤器不更新（项目已知 GQF 缺陷）。但因为「AppCode 为空 → 不过滤（降级为看全部）」，方向上偏安全，不会越权看到别人；只是可能漏隔离。用户/角色模块同受此影响（因实现 IHasAppCode）。

### ⚠️ 边缘（JWT 无 AppCode 的租户）
- 租户用户若 JWT 不含 AppCode claim：`UserService.GetUsersAsync`（:42-45）把 queryAppCode 置 null、`RoleService.GetRolesAsync`（:36）直接 null → 仓储/全局过滤器均不过滤 → 该租户能看到**全部**用户/角色。正常租户登录都带 AppCode（见 09:31 告警中心那次修复），属边界情形。

- 自定义角色（超管在「角色管理」建的新 Code，如 `finance_staff`）的权限**确实已落地 DB**：`Role.Permissions` 是 JSON 数组字符串（`Models/Role.cs:17` `// JSON array of permission strings`），`RoleService` 创建/更新时写入（前端 `adaptCreateRoleToBackend` 已传 `permissions`，`RoleRepository.GetByPermissionAsync` :42-51 也按此字段内存过滤，佐证其存在）。
- **但权限判定完全不读 DB，只查静态表**：
  - `Filters/PermissionFilter.cs:63-73` `GetUserPermissions(roleClaim.Value)` → `Roles.GetRolePermissions(roleClaim.Value)`。
  - `Configuration/RoleConfig.cs:17-28` 的 `switch` 对未知 Code 走 `_ => new List<string>()` → **空权限**。
  - 后果：持自定义角色的用户登录后，JWT `ClaimTypes.Role = "finance_staff"`，所有 `PermissionAuthorize` 保护的接口一律 403。
- **前端同样只读静态表**：`AuthContext.tsx` `hasPermission(perm)` → `getUserRole()` → `roles[user.role]`（静态 `DEFAULT_ROLES`，`permissions.ts`）→ 自定义 Code 查不到 → `hasPermission` 返回 false → **菜单/按钮整体不可见**，即使后端放开也看不到入口。
- `PermissionsController.GetCurrentUserPermissions`（:49）也走 `PermissionService.GetRolePermissions` → 静态 → 自定义角色调 `/api/v1/permissions/current` 返回空。
- 关键：角色 Code **全局唯一索引**（`AppDbContext.cs:225`）→ `role code → 单一 Role 记录` 无歧义，可按 Code 直接解析。

### 修复设计（单一事实来源 = DB `Role.Permissions`）
**后端**
1. `Services/PermissionService.cs` + `Interfaces/IPermissionService.cs`：新增 `List<string> GetEffectivePermissions(string roleCode)`：
   - `roleCode == Roles.SUPER_ADMIN` → 返回 `GetAllPermissionCodes()`（全部）。
   - 否则 `IRoleRepository.GetByCodeAsync(roleCode, appCode: null)`（**传 null 跨租户命中**，见 `RoleRepository.cs:17-21` `ApplyFilters` 在 appCode 为空不过滤）→ 命中则 `JsonSerializer.Deserialize<List<string>>(role.Permissions ?? "[]")` 返回（空/异常兜底为 `new List<string>()`）。
   - 未命中（如 5 个内置角色未落库）→ 回退 `Roles.GetRolePermissions(roleCode)` 静态，保证内置角色行为不变。
2. `Filters/PermissionFilter.cs:63-73`：改用 `context.HttpContext.RequestServices.GetService<IPermissionService>()?.GetEffectivePermissions(roleClaim.Value) ?? new()`（仿 :87 `TenantFilterAttribute` 的 RequestServices 取服务写法；服务为空兜底空列表）。超管短路（:37）保留。
3. `Controllers/PermissionsController.cs:49`：`GetCurrentUserPermissions` 改用 `GetEffectivePermissions(role)`，自定义角色也能拿到真实权限。
4. `Services/AuthService.cs`：给 `LoginAsync` / `GetCurrentUserAsync` / `SwitchCustomerAsync` 注入 `IPermissionService`，计算 `user.Role` 的有效权限并写入 `UserDto.Permissions`（让前端拿到实际权限集）。
5. `DTOs/Responses/UserResponse.cs`：`UserDto`（:6）加 `public List<string>? Permissions { get; set; }`。
   - （可选增强）`PermissionsController.GetAllRolePermissions`（:67）可顺带把 DB 里的自定义角色也并入返回，供前端角色矩阵展示；非必须。

**前端**
6. `Web/src/app/services/api/types/auth.types.ts`（及 `user.types.ts` 的 `UserDto`）：加 `permissions?: string[]`。
7. `Web/src/app/services/adapters/authAdapter.ts`：`adaptUserFromBackend`（:70）/ `adaptLoginResponseToUser`（:257）映射 `permissions`。
8. `Web/src/app/contexts/AuthContext.tsx`：
   - `User` 接口（:14-23）加 `permissions?: string[]`。
   - `hasPermission(perm)` 改为 `user?.permissions?.includes(perm) ?? false`（保留 `role==='super_admin'` 短路）。`roles`/`getUserRole`/`DEFAULT_ROLES` 保留用于**角色名与权限目录矩阵**（创建角色时的权限清单），仅「当前用户有效权限判定」切到服务端下发的列表。`Sidebar.tsx` 用 `hasPermission` 自动修复。

### 风险与边界
- `Role.Permissions` JSON 解析需防 null/空/格式错（兜底空列表，不抛）。
- 登录响应携带权限，存 `localStorage('user')`；角色权限变更后需**重新登录**才生效（与今日角色变更语义一致，可接受）。
- `GetByCodeAsync(code, null)` 依赖「Code 全局唯一」+「appCode 空不过滤」两前提，均已核实成立。
- 不改 JWT claim（保持 `GenerateToken` 现状），权限走响应体，避免 token 膨胀与失效难题。
