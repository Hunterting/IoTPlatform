### 6 个阻断级缺陷（BLOCKER）
- **B1 `param` 包装错误**：二开协议参数**平铺在 JSON 顶层**，无 `param` 层。现有 Builder 全部带 `param` → 所有带参命令设备无法解析

- **B4 遗嘱判定**：`willTopic` 允许与 `publishTopic` 相同，只能凭 `method=="close"` 判定；现有靠 `topic.StartsWith("/devtoser/will")` 硬编码 → 官方推荐配置下在线状态全错
- **B5 无品类能力校验**：喇叭类完全不支持 G3/G4 开关命令，WiFi 款不支持 G4/G5

### 报文里读出的 5 个协议事实
1. **`slots` 是状态数组，不是插槽编号列表**。`action on`→`[1]`，`action off`→`[0]`。若为编号列表，off 时应为 `[1]`。文档示例 `slots:[1,3,4]` 用状态数组解释不通（状态只能 0/1）→ **必须问安圣**。
2. **`tasks` 同名异构**：`getDevStatus.tasks[]`={voltage,status,power,slotNum,current} 是插槽电参数；`getDelayTasks.tasks[]`={cnt,sign,eAction,enable,sAction,secs} 是延时任务。**Parser 禁止跨 method 通用处理 `tasks`**。
3. **`sign` = 下发时的 frameId**。getDelayTasks 返回 `sign:"000000d7621a7844"` 正是 startDelayTask 的 frameId → **frameId 会被设备持久化成延时任务业务主键**，平台必须落库，否则无法精确取消某任务。直接影响 Phase 2 pending-store 设计。
4. **设备不校验下行 timestamp**。时钟被拨 +1h 期间，下发的服务器真实时间戳（慢1小时）全部返回 ok → 无时间窗校验、**无重放保护**。有利：平台无需与设备时钟同步即可下发。
5. **同值双序列化精度不一致**：`EMdata[0].v=226.2900085`(float32 噪声) vs `tasks[0].voltage="226.290"`(已舍入 string)；c/p 同理。**入库以 string 为准，或 EMdata 统一 round(3)**。

### ★ Q21 遗嘱测试结论：遗嘱未落在上行 topic 上

**测试方法**：
- v1: 15:04:08 起 180s 监听 `/iot/server/iot-board/863434084755211`，用户断电>30s后重上电
- v2: 15:07:45 起 30s 全量 `#` 订阅确认有无 retained 遗嘱

**时间线**：
- 15:04:09 设备在线（getDevStatus 正常应答）
- 15:04:?? 用户断电
- 15:04:??+30s broker keepAlive 超时 → **应在此时发布遗嘱**
- 15:05:21 设备重连，发布 `connected` 事件 (`firstBoot:true`)

**结果**：
- v1 180s 窗口内 ZERO `close` 报文在 `/iot/server/iot-board/863434084755211`
- v2 全量 `#` 30s ZERO `close`/retained 报文
- 唯一的新事件：设备重连时发布 `{"imei":"...","timestamp":...,"firstBoot":true,"method":"connected"}`

**结论（三种可能，按置信度排序）**：
1. **遗嘱 topic ≠ publish topic**（最可能）— 遗嘱落到了其他 topic 上，Phase1 的单订阅只覆盖了上行数据，不覆盖遗嘱。如果遗嘱 topic 是固定值而非 `+` 通配，甚至可能完全不匹配我们的订阅。
2. **设备 CONNECT 时未设置遗嘱**（备选）— 设备连接时 Will Flag=0，broker 无遗嘱可发。
3. **broker 有 Will Delay**（最不可能）— 遗嘱发布晚于监听窗口，但通常 keepAlive 超时后立即发布。

**对 Phase 1 的影响**：

- 如果遗嘱 topic 确实不同，需要**独立的遗嘱订阅**才能实现离线检测
